# Internationalization (i18n)

This document explains how translations work in the Podverse monorepo.

## Overview

Podverse uses a three-tier translation system:

```
originals/ → overrides/ → compiled/
```

1. **originals/**: Source translations (en-US is manually maintained, other locales are LLM-generated)
2. **overrides/**: Human corrections to LLM translations (empty by default, only non-empty values are used)
3. **compiled/**: Final merged output used by the application (generated at build time, not committed)

## Architecture

```
┌─────────────────────────────────────────────────────────────────┐
│                        COMMITTED TO GIT                         │
├─────────────────────────────────────────────────────────────────┤
│  originals/          │  overrides/                              │
│  ├── en-US.json      │  ├── es.json      (empty defaults)       │
│  ├── es.json         │  ├── fr.json      (empty defaults)       │
│  ├── fr.json         │  └── el-GR.json   (empty defaults)       │
│  └── el-GR.json      │                                          │
│  (LLM-generated)     │  (human overrides only)                  │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼ (at build time)
┌─────────────────────────────────────────────────────────────────┐
│                   GENERATED AT BUILD TIME                        │
├─────────────────────────────────────────────────────────────────┤
│  compiled/                                                       │
│  ├── en-US.json  (copy of originals)                            │
│  ├── es.json     (originals + non-empty overrides)              │
│  ├── fr.json     (originals + non-empty overrides)              │
│  └── el-GR.json  (originals + non-empty overrides)              │
└─────────────────────────────────────────────────────────────────┘
```

## Supported Locales

- `en-US` - English (United States) - **Source of truth**
- `es` - Spanish
- `fr` - French
- `el-GR` - Greek

## Apps with i18n

- `apps/web` - Main Podverse web application
- `apps/management-web` - Admin management interface
- `apps/mobile` - React Native app (planned; i18next + expo-localization)

## Shared catalog layers (target)

Medium-term, translation sources consolidate under `packages/i18n-catalog` with layered merge at
compile time (see **i18n-catalog-layers** rule and mobile master plan Track 17):

| Layer | Contents |
| ----- | -------- |
| `shared/` | Cross-app keys: `language.*`, common `errors.*`, `misc.*`, `settings.ui_theme.*` |
| `consumer/` | Web + mobile consumer namespaces (`media`, `features`, `authentication`, …) |
| `management/` | Management-web only (`dashboard`, `workers`, `admins`, …) |
| `mobile/` | RN-only overlay (permissions, store copy) — may start empty |

Per-app compiled output merges layers (later keys win). Web and management-web use next-intl;
mobile uses i18next. **Runtime must load `compiled/` output** so human `overrides/` apply (Track
17.0).

Until migration completes, each Next.js app keeps its existing `apps/*/i18n/` tree.

## Directory Structure

```
apps/web/
└── i18n/
    ├── originals/     # Source translations (committed)
    │   ├── en-US.json # Source of truth (manually maintained)
    │   ├── es.json    # LLM-generated
    │   ├── fr.json    # LLM-generated
    │   └── el-GR.json # LLM-generated
    ├── overrides/     # Human overrides (committed)
    │   ├── es.json    # Empty by default, non-empty = override
    │   ├── fr.json    # Empty by default, non-empty = override
    │   └── el-GR.json # Empty by default, non-empty = override
    └── compiled/      # Generated at build time (NOT committed)
        ├── en-US.json
        ├── es.json
        ├── fr.json
        └── el-GR.json
```

**Note**: `en-US` has no override file because it's the source language.

## Commands

### Run All i18n (Translate + Sync Overrides)

```bash
npm run i18n:all
```

This runs LLM translations for all non-English locales, then syncs override files.

### Translate Only (LLM)

```bash
npm run i18n:translate
```

Uses OpenAI to translate `en-US.json` to all other locales. Requires `OPENAI_API_KEY`.

### Compile / Sync Overrides

```bash
npm run i18n:compile
```

Syncs override file structure with originals (adds new keys with empty values) and generates compiled output. Does not require API key.

### Validate i18n Files

```bash
npm run i18n:validate
```

Checks that all translation files are valid and in sync. Used in CI.

### Per-App Commands

```bash
# Web app only
npm run i18n-compile -w apps/web
npm run i18n-llm-translations -w apps/web

# Management web only
npm run i18n-compile -w apps/management-web
npm run i18n-llm-translations -w apps/management-web
```

## Adding New Translation Keys

1. Add the new key to `apps/*/i18n/originals/en-US.json`
2. Commit and merge to `develop`
3. The automated workflow will:
   - Generate LLM translations for other locales
   - Sync override files (add new keys with empty values)
   - Commit the changes

**Optional**: Run `npm run i18n:all` locally to preview translations before merging.

## Adding a New Locale

**Important**: Locale definitions exist in multiple files that must stay in sync.

### Files to Update

| File                                                        | What to Update                     |
| ----------------------------------------------------------- | ---------------------------------- |
| `scripts/ci/validate-i18n.ts`                               | Add to `REQUIRED_LOCALES` array    |
| `apps/web/scripts/i18n/i18n-llm-translations.ts`            | Add to `targets` array             |
| `apps/management-web/scripts/i18n/i18n-llm-translations.ts` | Add to `targets` array             |
| `packages/notifications/.../i18nNotifications.ts`           | Add locale object manually         |
| `docs/localization/I18N.md`                                 | Update "Supported Locales" section |

### Steps

1. Add the locale to the `targets` array in both LLM translation scripts:

   ```typescript
   const targets = [
     { code: 'es', name: 'Spanish' },
     { code: 'fr', name: 'French' },
     { code: 'el-GR', name: 'Greek' },
     { code: 'NEW_CODE', name: 'Language Name' }, // Add new locale
   ];
   ```

2. Add the locale to `REQUIRED_LOCALES` in `scripts/ci/validate-i18n.ts`:

   ```typescript
   const REQUIRED_LOCALES = ['en-US', 'es', 'fr', 'el-GR', 'NEW_CODE'];
   ```

3. Update "Supported Locales" section in this documentation

4. Run `npm run i18n:all` to generate translations

5. Update `NEXT_PUBLIC_FEATURES_SUPPORTED_LOCALES` in `.env` files if needed

## Overrides System

Override files allow humans to correct LLM-generated translations:

- Override files have the **same structure** as originals
- All values default to **empty strings**
- **Non-empty values** override the LLM translation
- **Empty values** fall back to the original LLM translation

### How It Works

```json
// originals/es.json (LLM-generated)
{
  "features": {
    "podcast": "Pódcast",
    "episodes": "Episodios"
  }
}

// overrides/es.json (human corrections)
{
  "features": {
    "podcast": "Podcast",  // Non-empty = human override
    "episodes": ""         // Empty = use LLM translation
  }
}

// compiled/es.json (generated at build time)
{
  "features": {
    "podcast": "Podcast",   // Human override
    "episodes": "Episodios" // LLM translation
  }
}
```

### When to Use Overrides

- When the LLM translation is incorrect or awkward
- For brand-specific terminology that shouldn't be translated
- For technical terms that have better local equivalents

### Important: Human Overrides Are Sacred

Human override values are **never overwritten** by automated processes. When new keys are added to originals, they appear in overrides with empty values, preserving all existing human corrections.

## CI Validation

**Note**: i18n validation runs in the `i18n-translate.yml` workflow (after merge to develop), NOT during PR validation.

This allows contributors to:

1. Only update `en-US.json` in their PRs
2. Optionally update override files to fix translations

The validation checks:

1. **Required files exist**: All locale files in originals, override files for non-source locales
2. **Key alignment**: All locales have the same keys as `en-US.json`
3. **Key ordering**: Keys are in the same order as `en-US.json`
4. **No empty values in originals**: LLM should generate complete translations
5. **Override structure matches originals**: Same keys (empty values allowed)

**Note**: `compiled/` is NOT validated - it's generated at build time.

## Automated Translation Workflow

When PRs are merged to `develop`, a GitHub Actions workflow automatically:

1. Detects if any `en-US.json` files were changed
2. Runs LLM translations for all non-English locales
3. Syncs override files (adds new keys with empty values)
4. Validates the files
5. Commits and pushes `originals/` and `overrides/` to `develop`

### How It Works

- **Trigger**: Push to `develop` that modifies `apps/*/i18n/originals/en-US.json`
- **Workflow**: `.github/workflows/i18n-translate.yml`
- **Requires**: `OPENAI_API_KEY` repository secret

### What Gets Committed

Only `originals/` and `overrides/` are committed. The `compiled/` folder is generated at build time by the `prebuild` script.

### Override-Only PRs

Contributors can create PRs that only update override files (to fix translations). These PRs:

- Do NOT trigger the auto-translate workflow (en-US unchanged)
- Are merged directly
- The human overrides are preserved

## OpenAI API Key Setup

LLM translations require an OpenAI API key:

### Local Development

Create `.env.openai` at the **root** of the monorepo (shared by all apps):

```bash
# Copy the example file
cp .env.openai.example .env.openai

# Edit and add your API key
# .env.openai
OPENAI_API_KEY=sk-...
```

### GitHub Actions (CI)

Add `OPENAI_API_KEY` as a repository secret:

1. Go to repository Settings → Secrets and variables → Actions
2. Add a new repository secret named `OPENAI_API_KEY`
3. The CI workflow will automatically use it for LLM translations

## Translation Cache

LLM translations are cached locally to avoid redundant API calls:

- Cache location: `apps/*/.translation-cache.json`
- Cache is keyed by locale, key path, AND source value hash
- If a source value changes, the cache detects this and re-translates
- To force re-translation of everything, delete the cache file

**Note**: `.translation-cache.json` is gitignored and should not be committed.

## Special Case: Notifications Package

The `packages/notifications` package uses a **TypeScript-based** translation file instead of JSON:

**File:** `packages/notifications/src/services/notifications/i18nNotifications.ts`

```typescript
export const i18nNotifications: Record<string, NotificationLocaleMap> = {
  'en-US': {
    'livestream-started': 'Live: ',
    'livestream-scheduled': 'Live Scheduled: ',
    // ... other message types (empty placeholders)
  },
  es: {
    /* ... */
  },
  // ...
};
```

**Why TypeScript instead of JSON:**

- Type safety with `NotificationMessageType` enum
- Runtime usage in a package (no build step like Next.js)
- Very few strings (9 types, only 2 have values)

**When adding a new locale:**

1. Add the locale object to `i18nNotifications`
2. Manually translate the active strings

This file is NOT part of the automated i18n system.

## Best Practices

1. **Only commit originals and overrides** - compiled is generated at build time
2. **Review LLM translations** before merging PRs with translation changes
3. **Use overrides for corrections** - don't manually edit originals (except en-US)
4. **Keep en-US.json as the source** - all other translations derive from it
5. **Run validation locally** before pushing: `npm run i18n:validate`
