# Internationalization (i18n)

This document explains how translations work in the Podverse monorepo.

## Overview

Podverse uses a three-tier translation system:

```
originals/ → overrides/ → compiled/
```

1. **originals/**: Source translations for every locale. `en-US` is the source of truth. Other
   locales are written in the same trees by agents or people (not by an OpenAI job).
2. **overrides/**: **Operator-only** corrections (empty by default). Non-empty values win at compile.
   Agents do not edit override files.
3. **compiled/**: Final merge used by the apps (generated at build time, not committed)

## Architecture

```
┌─────────────────────────────────────────────────────────────────┐
│                        COMMITTED TO GIT                         │
├─────────────────────────────────────────────────────────────────┤
│  originals/          │  overrides/                              │
│  ├── en-US.json      │  ├── es.json      (empty defaults)       │
│  ├── es.json         │  ├── fr.json      (empty defaults)       │
│  ├── fr.json         │  └── el-GR.json   (empty defaults)       │
│  └── el-GR.json      │                                          │
│  (all locales)       │  (operator corrections only)             │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼ (at build time)
┌─────────────────────────────────────────────────────────────────┐
│                   GENERATED AT BUILD TIME                        │
├─────────────────────────────────────────────────────────────────┤
│  compiled/                                                       │
│  ├── en-US.json  (copy of originals)                            │
│  ├── es.json     (originals + non-empty overrides)              │
│  ├── fr.json     (originals + non-empty overrides)              │
│  └── el-GR.json  (originals + non-empty overrides)              │
└─────────────────────────────────────────────────────────────────┘
```

## Supported Locales

- `en-US` - English (United States) - **Source of truth**
- `es` - Spanish
- `fr` - French
- `el-GR` - Greek

## Apps with i18n

- `apps/web` - Main Podverse web application
- `apps/management-web` - Admin management interface
- `apps/mobile` - React Native app (i18next + expo-localization)

## Shared catalog layers

Translation **authoring** lives under `packages/i18n-catalog` with layered merge at compile time
(see **i18n-catalog-layers** rule):

| Layer         | Contents                                                                         |
| ------------- | -------------------------------------------------------------------------------- |
| `shared/`     | Cross-app keys: `language.*`, common `errors.*`, `misc.*`, `settings.ui_theme.*` |
| `consumer/`   | Web + mobile consumer namespaces (`media`, `features`, `authentication`, …)      |
| `management/` | Management-web only (`dashboard`, `workers`, `admins`, …)                        |
| `mobile/`     | RN-only overlay (permissions, store copy) — may start empty                      |

Per-app compiled output merges layers (later keys win). Web and management-web use next-intl;
mobile uses i18next. **Runtime must load `compiled/` output** so operator `overrides/` apply.

For Next.js apps, runtime message loading paths are:

- `apps/web/src/i18n/request.ts`, `apps/web/src/app/layout.tsx`,
  `apps/web/src/app/global-error.tsx`
- `apps/management-web/src/i18n/request.ts`, `apps/management-web/src/app/layout.tsx`,
  `apps/management-web/src/app/global-error.tsx`

Web and management-web run `i18n-compile` in `predev` and `prebuild` to ensure
`i18n/compiled/*.json` exists before app startup/build. Mobile runs `i18n-compile` in `prestart`,
`preios`, and `preandroid`.

## Directory Structure

```text
packages/i18n-catalog/          # authoring source of truth
├── shared/{originals,overrides}/
├── consumer/{originals,overrides}/
├── management/{originals,overrides}/
└── mobile/{originals,overrides}/

apps/web/i18n/compiled/*.json              # generated only
apps/management-web/i18n/compiled/*.json   # generated only
apps/mobile/i18n/compiled/*.json           # generated only
```

Layer and app `compiled/` trees are **gitignored** (regenerated by `npm run i18n:compile`).

**Note**: `en-US` has no override file because it's the source language. Do **not** keep
app-local `originals/` or `overrides/` under `apps/*/i18n/`.

## Commands

### Compile / Sync Overrides

```bash
npm run i18n:compile
```

Syncs layer override structure with originals (adds empty slots for new keys; never overwrites
non-empty operator values) and generates layer and app compiled outputs.

### Validate i18n Files

```bash
npm run i18n:validate
```

Checks layer structure, locale key parity, duplicate key paths between layers, and empty `en-US`
values.

### Per-App Commands

```bash
# Web app prebuild hook target
npm run i18n-compile -w @podverse/web

# Management web prebuild hook target
npm run i18n-compile -w @podverse/management-web

# Mobile prestart hook target
npm run i18n-compile -w @podverse/mobile
```

## Adding New Translation Keys

1. Add the key to the correct layer under `packages/i18n-catalog/`:
   - shared: `packages/i18n-catalog/shared/originals/en-US.json`
   - consumer (web + mobile): `packages/i18n-catalog/consumer/originals/en-US.json`
   - management: `packages/i18n-catalog/management/originals/en-US.json`
   - mobile-only: `packages/i18n-catalog/mobile/originals/en-US.json`
2. Add the same key path in `es.json`, `fr.json`, and `el-GR.json` in that layer, with a
   translation in each language (not English title case copied over). Keep `{placeholders}`
   identical to `en-US`.
3. Do not edit `overrides/`. Compile adds empty override slots for new keys.

English chrome uses title case; sentences use sentence case. See **ui-copy-casing**.

## Adding a New Locale

**Important**: Locale definitions exist in multiple files that must stay in sync.

### Files to Update

| File                                              | What to Update                     |
| ------------------------------------------------- | ---------------------------------- |
| `packages/i18n-catalog/scripts/i18n-validate.ts`  | Add to `REQUIRED_LOCALES` array    |
| `packages/i18n-catalog/scripts/i18n-compile.ts`   | Same locales list if present       |
| `packages/notifications/.../i18nNotifications.ts` | Add locale object manually         |
| `docs/localization/I18N.md`                       | Update "Supported Locales" section |

Then add `originals/<code>.json` (and empty-structure `overrides/<code>.json`) in every layer.
Update `NEXT_PUBLIC_FEATURES_SUPPORTED_LOCALES` in `.env` files if needed.

## Overrides System

Override files allow operators to correct a translation without editing `originals/`:

- Override files have the **same structure** as originals
- All values default to **empty strings**
- **Non-empty values** override the original
- **Empty values** fall back to the original

### How It Works

```json
// originals/es.json
{
  "features": {
    "podcast": "Pódcast",
    "episodes": "Episodios"
  }
}

// overrides/es.json (operator corrections)
{
  "features": {
    "podcast": "Podcast",
    "episodes": ""
  }
}

// compiled/es.json (generated at build time)
{
  "features": {
    "podcast": "Podcast",
    "episodes": "Episodios"
  }
}
```

### When to Use Overrides

- When the original translation is incorrect or awkward and the operator wants a local fix
- For brand-specific terminology that shouldn't be translated
- For technical terms that have better local equivalents

Human override values are **never overwritten** by compile. When new keys are added to originals,
they appear in overrides with empty values.

**Agents never edit override files.**

## CI Validation

`.github/workflows/i18n.yml` runs `npm run i18n:validate` on pull requests that touch
`packages/i18n-catalog`. It does not generate or commit translations.

The validation checks:

1. **Required files exist**: All locale files in originals, override files for non-source locales
2. **Key alignment**: All locales have the same keys as `en-US.json`
3. **No empty values in en-US originals**
4. **Override structure matches originals**: Same keys (empty values allowed)

**Note**: `compiled/` is NOT validated — it's generated at build time.

## Special Case: Notifications Package

The `packages/notifications` package uses a **TypeScript-based** translation file instead of JSON:

**File:** `packages/notifications/src/services/notifications/i18nNotifications.ts`

**Why TypeScript instead of JSON:**

- Type safety with `NotificationMessageType` enum
- Runtime usage in a package (no build step like Next.js)
- Very few strings (9 types, only 2 have values)

**When adding a new locale:**

1. Add the locale object to `i18nNotifications`
2. Manually translate the active strings

This file is NOT part of the JSON catalog compile.

## Best Practices

1. **Only commit originals and overrides** — compiled is generated at build time
2. **Write every required locale in originals** when adding keys
3. **Use overrides for operator corrections** — agents fix `originals/` instead
4. **Keep en-US.json as the source** — other locales follow its keys and placeholders
5. **Run validation locally** before pushing: `npm run i18n:validate`
