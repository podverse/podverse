# Push permission on a new device

## Request

When a user signs into a device and that user has never been presented with the option to enable push notifications yet, but the user has in their settings saved to the database that they should have push notifications enabled for at least one item, then the browser or mobile app should automatically ask them once if they want to enable push notifications. The use case goes that sometimes users may be logged into one device and maybe they go through the whole process of enabling push notifications on that device, but then at a later time they sign into a different device for the first time and they have notifications enabled on our back end. The device still needs to ask for permission, but we don't want to ask them for that permission unless they already have notifications saved. Otherwise, the notification enable feature should happen the first time they try to add notifications on that device.

I think we want to preserve our existing pop-up request for notifications process, but there is this one scenario we want to add where the user signs into a different device when they already have notifications on another device. Furthermore, double check that the way we have notifications set up now is that if a user for the very first time anywhere presses the notification button on a device and they don't have push notifications enabled, that it will ask them if they want to enable push notifications. However, if they already received that notification due to the scenario I have described, where they have two different devices and they signed into the second device and they already were asked this, then that action shouldn't display the automatic enable push notifications pop up. Instead, the user is expected to go into their notification settings and manually enable push notifications in there. And also, there should be a warning banner at the top of the notification settings screen if a user has push notifications enabled but does not have push notifications enabled for that device. And there should be a button in that warning banner. That they have push notifications but have not given permission to receive push notifications on this device. It should be warning colors instead of danger, actually, and it should be at the very top of the notification screen. If the user has no push notification settings enabled, they should not see this banner. It is only to be displayed when the user has them enabled, but hasn't granted this device permission for them.

## Operator answers

- **What counts as push already enabled:** "At least one notification setting has Push turned on (new episodes, livestreams, and the other category toggles)." A show's notification bell being on does not, by itself, count.
- **What the one-time ask looks like:** "A short in-app dialog: enable push on this device, or not now. Yes asks the system for permission and registers this device. No only records that we asked. Settings stay unchanged." Do not reuse the Subscribe dialog (Enable Push / In-App Only). That dialog stays for Subscribe. Choosing In-App Only there can turn account push settings off when the account has no registered device, and this ask must not change those settings.
- **When it appears:** "Only right after they sign in on this device." Do not also ask on a later open of an already-signed-in session.
- **Banner button:** "I would like for it to prompt the user again with the native dialogue, but if that is forbidden by mobile devices, then do whatever the best practice is. I guess the fallback behavior would be to pop up information that guides them to easily enable the settings themselves. If there is a link that we can show them or a button that can take them directly to the notification settings for Podverse, then we want to do that."

Settled reading for planning: web and mobile. After a fresh sign-in, if this account on this device has never been shown this dialog, and at least one notification category has push turned on, and this device has not granted push permission, show the short dialog once. Yes requests the system permission and registers this device. Not now records that the dialog was shown. Neither answer changes category push settings. Record "shown" only after the dialog is actually presented, so a sign-in that never shows it can still ask on a later sign-in. After it has been shown on this device, the channel notification control must not show an automatic enable-push prompt; the person turns this device on from notification settings. The banner is warning (not danger), at the very top of the notification settings screen, on web and mobile. It shows only when at least one category has push on and this device has not granted permission. Its button requests the native permission dialog again. When the platform will not show that dialog again, guide them, and when the platform can open Podverse's own notification settings, give a control that goes there.

### Review of the first planning pass

These answers settle D1–D20. Where this section disagrees with the settled reading above, this section wins.

- **D1 — Sign-in dialog.** Show it only when the account already has a registered push device somewhere (FCM, Web Push, or Unified Push) and at least one category has Push on, and this device can still be asked. A new account with only the seeded defaults is not asked.
- **D2 — Settings banner.** Same rule as the dialog: a registered push device somewhere, a category with Push on, and this device has not allowed notifications. New accounts that only have the seeded defaults do not see it.
- **D3 — Already-blocked device.** Skip the sign-in dialog and do not record it as shown. The settings banner and its guidance cover that device.
- **D4 — Cannot receive push.** A browser or app build that cannot receive push gets neither the dialog nor the banner.
- **D5 — Dialog-shown flag.** Stored on this device, per account, and kept after sign-out. This account is asked only once on this device.
- **D6 — Unified Push on the website.** A Unified Push registration counts as every browser already enabled. No dialog, no banner, and turning on Web Push must not run. That keeps the existing step that deletes a Unified Push device from running.
- **D7 and D15 — Channel bell after a refusal.** "When someone turns notifications on and they refuse the push notification, whether that be web or mobile, we still want the notification to turn on because they will begin getting inbox notifications, which don't require push notifications necessarily. If this isn't the behavior currently, this is the behavior we need for both mobile and web." Both surfaces turn the channel's notifications on even when the person refuses the system prompt. The website changes from leaving the channel off after a refusal. When the bell does not prompt, it still turns the channel on, as planned.
- **D8 — Warning banner component.** The shared web `Banner` (`packages/ui`) exists and its only variant is `danger`. "Even if this is only the first time we're using a banner of this style, let's make it a component that could potentially be used elsewhere on the site." Add a warning variant to that shared banner and use it on the website. The app keeps its own banner; it does not use `@podverse/ui`.
- **D9 and D16 — Subscribe prompt.** The first-Subscribe prompt keeps its own answered flag and can still appear after the sign-in dialog.
- **D10 — Google push before registration.** On an FCM build, this phone counts as enabled as soon as notification permission is granted. Background sync registers it without asking again.
- **D11 — Unregistered Unified Push.** An unregistered Unified Push build counts as unable to receive push. No dialog, no banner. Setup stays in More › Advanced.
- **D12 — How the app detects sign-in.** Watch the account change from signed out to signed in. A cold start with a saved session stays signed in and does not ask. Do not use the sync layer's sign-in signal.
- **D13 — Terms and Taste Profile.** The dialog waits until those screens are finished, so it does not open underneath them.
- **D14 — Sign-in check.** Runs at the end of sign-in, outside the sync queue. A failure only logs a warning.
- **D17 — After they refuse the system prompt from the banner.** Nothing here turns notifications off for good. "Blocked" means the phone will not show its permission prompt again. They can still turn notifications on later. Leave the banner up. The next tap of Allow on This Device, once the phone will not ask again, opens the Notifications Are Blocked dialog, whose Open System Settings button goes to Podverse's notification settings.
- **D18 — Lower permission hint.** "I think we can get rid of the lower hint on mobile and web since the warning banner should be sufficient for that purpose." The website has no matching hint. Remove the app's lower permission hint entirely (`more-settings-notification-permission-hint` and its Open System Settings link), including when the banner is not showing.
- **D19 — Open System Settings.** Use the linking tools already in the app. Android opens Podverse's own notification page, falling back to the app info page if the phone refuses that page. iPhone opens Podverse's page in Settings. Do not add `expo-application`.
- **D20 — Returning from system settings.** If notifications go from not allowed to allowed while the person is in system settings, register the phone as soon as they return to the notification settings screen.

## Glossary

- **Notification button:** the control that turns notifications on or off for one show (the channel bell), not the inbox bell.
- **At least one item:** at least one notification category whose Push setting is on. See Operator answers.

## Orientation

Checked while writing this file.

- Web Subscribe dialog is Enable Push / In-App Only. It is separate from the system permission prompt. `apps/web/src/components/Media/Header/SubscribeButton.tsx` mounts it. `apps/web/src/lib/notifications/firstSubscribePushPrompt.ts` stores `podverse.subscribe_push_prompt_answered:<accountIdText>` in localStorage, and `applyFirstSubscribePushChoice` turns media category push off when the choice is in-app only and the account has no FCM, web push, or Unified Push device.
- Mobile Subscribe uses the same two choices. `apps/mobile/src/hooks/useFirstSubscribePushPrompt.tsx` and `apps/mobile/src/lib/notifications/applyFirstSubscribePushChoice.ts`. The answered flag is AsyncStorage `notifications.subscribe_push_prompt_answered:` in `apps/mobile/src/prefs/subscribePushPromptPrefs.ts`.
- Web channel bell: `apps/web/src/components/Media/Header/NotificationIconButton.tsx`. When `Notification.permission` is not `granted`, turning notifications on calls `requestNotificationPermission` in `apps/web/src/lib/notifications/webpush/requestNotificationPermission.ts` before creating the channel notification row. It does not check category push settings or the Subscribe answered flag.
- Mobile channel bell: `apps/mobile/src/hooks/useChannelNotifications.ts`. The portion read does not call `Notifications.requestPermissionsAsync`. System permission lives in `apps/mobile/src/push/fcmTransport.ts` (`getFcmPermissionStatus`, `requestPermissionsAsync`).
- Web notification settings: `apps/web/src/components/Settings/Panels/SettingsNotifications/SettingsNotifications.tsx`, mounted from `apps/web/src/components/Settings/Settings.tsx` when the notifications tab is open. Push permission for settings controls also goes through `apps/web/src/components/Settings/Panels/SettingsNotifications/usePushChannelControls.ts`.
- Mobile notification settings: `apps/mobile/src/screens/more/MoreSettingsNotificationsScreen.tsx`. It already has a lower permission hint (`more-settings-notification-permission-hint`) and, when permission is blocked, `openSystemNotificationSettings` on `more-settings-open-notification-settings`. That hint is not a top-of-screen warning banner gated on category push being on.
